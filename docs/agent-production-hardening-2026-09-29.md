## Failure evidence and implemented repairs

The earlier firmware incident is reconstructed in [agent-repair-incident-2026-09-28.md](agent-repair-incident-2026-09-28.md). Its generated C++ failed to compile; one deterministic include repair did not resolve the remaining diagnostics, and the run exhausted its budget. The historical rejection did not record its attempted charge, so its exact provider-budget dimension remains unknown. The isolated repaired copy now compiles for `esp32dev`.

The later run `agent-run-39c680f22c5049088f7b15a6938f2556` stopped with `AGENT_RUNTIME_NO_PROGRESS` after five generated files and no build. Saved turns 11–16 show repeated list/read operations, an unchanged write, and a plan update. Independently, replaying its observations through the native planner exposed a concrete harness defect: positional observation tracking generated false `tool_result_missing` responses after compaction, and revised task text was not reliably delivered. This defect can mislead repair; the trace does not prove it was the only cause of that run's failure.

The native planner now associates completed results with stable call IDs, rejects genuinely missing results, delivers task revisions explicitly, and bounds tool-output previews without truncating JSON mid-object. A single runtime deadline governs provider calls, dependency validation, and builds. Standard jobs retain 15 minutes, 100 tools, 120 model API requests, 245,760 reserved output tokens, and 8 MB cumulative input. Advanced jobs allow 45 minutes, 300 tools, 360 requests, 737,280 output tokens, and 24 MB input. Both keep cumulative consumption on resume. The prior 900-second runtime clamp that would have defeated Advanced was removed.

The task checkpoint and run projection now include a versioned task-state view: revision history, requirements, exclusions, decisions, current milestone, expected paths, evidence references, blockers, failed approaches, next action, and recovery state. Three stale turns initiate one bounded reorientation; two more ineffective turns stop with `AGENT_RUNTIME_NO_PROGRESS`. Registry command failure is classified as infrastructure unavailability, receives one bounded retry, and does not trigger source repair or claim a library is missing. The release quality verifier now requires 86/90 attempts, at least 2/3 per scenario, every historical repetition, and request-fidelity reviews. The separate release verifier still requires signed installer, hardware cycles, and clean-machine recovery evidence.
